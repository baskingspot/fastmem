### Granite Rapids composition

Copy and move paths at every length from 0 through 64 have identical executed instruction bytes to the measured pairs binary.
Set paths at every length from 0 through 1024 have identical executed instruction bytes to the measured chunks binary.
The complete set function matches after branch-target normalization, but its raw bytes differ.
All three complete large kernels match both measured references byte for byte.

Medium copy and move paths do not match the measured chunks bytes.
The differences at every length from 65 through 1024 are:

- The return-register copy moves from the end to the start.
- Stores use `%rax`, which holds `%rdi`, as their destination base.
- The entry takes one additional branch.
- The move entry uses `n > 63` instead of `n >= 64`.

Normalization of these specific differences leaves no other instruction difference across all 1920 copy/move paths.
That comparison does not establish equal latency.
The extra taken branch is a concrete composite performance risk.

### Zen 5 composition

The complete composite `.text` differs from the measured source64 image in exactly six bytes.
Those bytes encode two NT comparisons, one in `copyLarge` and one in `largeKernel`.
Both comparisons change from `0xc00001` to `0x2000000`.
All other `.text` bytes match.
The 288-byte `forwardSource` function is unchanged.

The older one-MiB source candidate also differs in its forward-overlap threshold and predicate order.
It is not a byte-identical reference for the source64 policy.
Against pre-composite main, the composite changes the large copy/move paths and their relative transfers.
The set kernels retain their bytes.

### Gap 2: Zen 5 temporal fill

The control source has four stores per iteration in `src/x86_64/set.zig:large`.
LLVM emits a 32-store main loop with a 2048-byte advance.
The local control loop spans `0xa350` through the backedge at `0xa458`.
Its remainder loop has four stores.
The complete `largeKernel` occupies 469 bytes in the control probe.

The `x86g_temporal` experiment keeps the existing head, tail, and thresholds.
It places the existing four-store body inside one assembly loop.
The candidate loop spans `0xa2f3` through the backedge at `0xa317`.
It has seven instructions and advances 256 bytes.
The complete `largeKernel` occupies 144 bytes.

The behavioral reference also uses four aligned stores per temporal iteration.
The reference is `.bench-cache/glibc/x86g/c8a-memset.asm`, addresses `0x196c80` through `0x196ca6`.
The implementation derives from fastmem's existing loop, not from the reference instructions.
No glibc instructions enter tracked files.

For every destination alignment, the initial offset is 193–256 bytes.
The head covers bytes 0–255.
Each iteration starts below `n - 256` and stores 256 bytes.
The tail covers the final 256 bytes.
These intervals cover the destination without an access beyond its bounds.

Exactly 48 MiB already selects NT in `6135cac`: the comparison is `n >= 0x3000000`.
This candidate addresses 32 MiB and other temporal sizes below 48 MiB.
It does not address an exact-48-MiB regression.
The 48-MiB NT threshold and the grouped NT loop remain unchanged.

### Gap 3: Zen 4 small copy and move

The stated 2.73-ns compiler-rt timing does not describe the final-standard tiny-move rows.
The measured compiler-rt entry is `memmove` at `0x10ac990`.
Fastmem's move entry is `x86_64.move.moveKernel` at `0x10956c0`.
Both use byte snapshots for 1–3 bytes.
Compiler-rt uses a branchless four-word class for 4–15 bytes.
Fastmem uses two-word classes after four size tests.

| Case | Fastmem ns | Compiler-rt ns | Fastmem instructions/iteration | Compiler-rt instructions/iteration |
|---|---:|---:|---:|---:|
| move/disjoint/0 | 2.181 | 1.364 | 12 | 14 |
| move/disjoint/1 | 2.455 | 1.637 | 21 | 23 |
| move/disjoint/4 | 2.728 | 1.636 | 21 | 26 |
| move/disjoint/8 | 2.727 | 1.637 | 21 | 26 |
| copy/aligned/24 | 3.000 | 1.780 | 19 | 29 |

The instruction counts come from the saved hardware counters and include the timed loop.
Fastmem retires fewer instructions in each row but takes more cycles.
A smaller instruction count therefore does not explain or solve this gap.
Code layout or branch throughput remains an unverified cause.

The gap31, gap33, and disjoint move rows at 4–15 bytes commonly lose by 1.67x.
The gap1 rows usually win.
The forward-half overlap at 8 bytes loses by 3.23x and needs separate attention.
Zero and 1–3-byte rows also contribute to the tier loss.

For copy, the 16-byte row loses by about 1.28x.
Most 24–32-byte rows lose by about 1.57x.
Fastmem's 17–32-byte entry takes two branches before its XMM pair.
The measured copy entry starts at `0x1094d90`, with that pair at `0x1094e3b`.
No replacement is selected here.
The rejected one-byte candidate does not address the dominant 4–15-byte move rows.

### Gap 4: Granite Rapids 65–256 bytes

The copy and move entries share `x86_64.move.kernel` at `0x1093970` in the measured binary.
The entry branch at `0x1093977` sends medium lengths to the block at `0x10939e5`.
The 96-byte path has ten instructions and one taken branch.
The 192-byte path has sixteen instructions and two taken branches.

The largest losses concentrate in non-dependent 96–128-byte rows.
Copy/aligned/128 takes 1.553 ns against glibc's 1.036 ns.
Move/disjoint/128 takes 1.551 ns against 1.036 ns.
Most short-gap overlap rows at these sizes remain near parity.
At 192 and 256 bytes, the aligned copy loss is about 1.16x.
Misaligned copy is near parity at those sizes.

The `x86g_medium` experiment changes only the medium-entry branch hint on Granite Rapids.
The 96-byte path keeps ten instructions but has no taken branch.
The 192-byte path keeps sixteen instructions but has one taken branch.
The memory instructions retain their classes and widths.

This layout adds one taken branch to the 0–63-byte paths.
The experiment can lose the existing pairs gains.
The standard fleet A/B must include those rows, not only the medium tier.
The runtime-dispatch bounded entry does not use this hint.

### Gap 5: Sapphire Rapids 257–1024 bytes

The measured copy entry starts at `0x10939b0`.
Its local control probe has the following complete paths:

| Size | Instructions | Conditional branches | Taken branches | Vector loads and stores |
|---|---:|---:|---:|---:|
| 384 | 26 | 6 | 4 | 12 |
| 512 | 30 | 6 | 5 | 16 |
| 768 | 40 | 7 | 5 | 24 |
| 1024 | 48 | 7 | 6 | 32 |

The head/tail chunks already remove redundant transfers at 384 and 768 bytes.
The remaining losses are not uniform across alignment profiles.
Copy/aligned/512 takes 3.848 ns against glibc's 2.733 ns, a 1.41x loss.
The 384-byte misaligned rows win at about 0.77x.
The 768-byte misaligned rows lose at about 1.13x.
The 1024-byte misaligned rows lose at about 1.22x, while aligned/1024 wins at 0.86x.

A split-cache-line throughput limit is plausible for the large misaligned classes, but remains unverified.
A balanced size tree reduces the upper-class decisions at the expense of the accepted 65–256-byte paths.
No new selection is justified by these static counts alone.
The Sapphire Rapids medium classes remain unchanged.
